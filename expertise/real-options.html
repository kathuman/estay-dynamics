Expertise 03 · Real Options

Pricing the value of not deciding everything today.

You're being asked to commit capital to a network decision today — build the facility, lock the capacity — against a demand forecast nobody fully trusts. A standard NPV analysis prices exactly one path through that decision and stops there. It can't price the alternative — wait for more information, build smaller and expand later, or walk away — because those aren't cash flows, they're choices. Real options analysis prices the choices.

That flexibility isn't just a qualitative hedge-your-bets argument — it has a quantifiable value, and leaving it out of the analysis is a real modeling error, not a conservative simplification. A design that can be staged or expanded is worth more than an equally-costed rigid one whenever the future is genuinely uncertain, and a decision process that can't price that difference will keep choosing the rigid option by default, not because it's actually better.

Real options theory, borrowed from financial options, is what prices it: a real option is the right, not the obligation, to take some future action — expand a facility, defer a commitment, switch a sourcing strategy, abandon a site — once more information has arrived. That right has value even before you exercise it, and a static commit-now NPV that ignores it will systematically undervalue flexible designs relative to rigid ones, because it's implicitly assuming the future demand path is already known.

The practical technique is a demand (or cost, or disruption) lattice — a binomial tree of how the uncertain quantity could evolve — solved backward from the future toward the present, so that at each node the model asks "given what's now known, what's the best available choice, and what's it worth?" instead of asking that question only once, today, under today's assumptions.

This connects directly to network design optimization: real options is the framework for pricing flexibility across time (when to commit); stochastic and mixed-integer programming is the framework for pricing flexibility across configurations (what to commit to). A network decision usually needs both.

Reference
Core question
Given genuine uncertainty, what is the value of the right to wait, stage, expand, or abandon — and does it change which option actually looks best today?
Business value
A number for what flexibility is actually worth, so a staged or deferred design can compete honestly against a cheaper-looking commit-now plan instead of losing to it by default.
Core method
A binomial demand lattice solved by backward induction, comparing a commit-now strategy against wait-and-see and staged-expansion alternatives at every node.
